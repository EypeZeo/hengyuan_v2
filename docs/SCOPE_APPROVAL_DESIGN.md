## 1. 目标与原则

目标：Owner 一次签署“在什么边界内可以自动下单”，执行核心在边界内自动下单，不再逐单人工确认；边界之外一律拒绝；Owner 随时可以收紧；任何放宽都需要他的硬件密钥。R-24 决定不建远程写通道，所以没有审批服务：签署在 Owner 的本机完成，范围是一份自证的签名文件。

六条原则，后文每一条规则都是它们的推论：

1. **放宽需要签名，收紧不需要。**增加授权的唯一途径是 Owner 的硬件密钥对一份新范围的签名；撤销、熔断、让范围过期都是本机命令或自然发生，不需要任何签名。
2. **范围是机器门的合取，不是替代。**它只替代 Gate 11 的逐单**人工**确认；Gate 1 至 10、12 至 12d 与最终门（`5.9.2`）的七项照旧，熔断永远优先；范围的限额只能窄于机器硬上限，不能抬高它。
3. **范围不可变、带序号。**改变范围 = 签一份新序号的范围，旧的被终结；不存在就地编辑，也不存在“延期”。
4. **花出去的额度只凭“没发出”的正向证明归还。**其余一律按“可能已花”（沿用 NotSent 的原则：NotSent 只能是正向事实）。
5. **失败关闭。**签名、存储、时钟、账本任何一项不可信，就拒绝；不降级为“没有范围检查”，也不降级为“用本地时钟”。
6. **范围只管增加风险的订单。**只减风险的退出不消耗额度、也不被范围挡住（它走 `5.9.5` 的通道，依赖任务 1A.7）；否则范围过期、被撤销或额度耗尽时，反而平不了仓。

## 4. 签署、安装与撤销（本机流程，没有审批服务）

- **签署**在 Owner 的本机（插着硬件密钥的那台机器）：`hy_scope sign`。输入：从执行主机读到的存储身份（`store_uuid`、`environment`、`account_uid`、当前序号高水位）和额度参数；输出：一个范围文件。签署前工具在终端打印**可读摘要与它的哈希**；Owner 在执行主机上用 `hy_scope status` 看到同一个哈希才继续（带外确认，缓解 L-66“没有可信屏幕”：被篡改的签署工具能让他签出比他看到的更宽的范围，而执行侧的机器硬上限是最后一道）。
- **传输**：文件经任何通道到执行主机。**通道不需要可信**：签名自证，篡改一个字节就验不过。
- **安装**在执行主机：`hy_scope install <文件>` 经本机进程间通信（权限受限的套接字，核对对端身份）交给运行中的执行核心。工具不直接写日志（只有执行核心写持久日志）。执行核心因此只多了一个本机入口，只接受三种消息：`Install(范围字节)`、`Revoke(serial)`、`Status`（只读）。
- **安装检查**，顺序固定，任一失败即拒绝并留审计，不部分应用：① 长度、格式、版本；② `environment`、`account_uid`、`store_uuid` 与存储的绑定一致；③ `sig_alg` 与 `key_id` 在本环境的受信表里；④ 验签；⑤ `serial` 大于持久高水位，且该序号没有待决的撤销；⑥ 有效期：`not_after` 距现在不超过有效期上限（D7），且按 §7 的上界估计尚未过期；⑦ 各项额度不大于机器硬上限；⑧ Production：存储里已有 Owner 的首单声明（§10、D5）。
- **持久**：一次原子的控制面追加 `ScopeInstalled`（整份范围字节与签名，使恢复不依赖原文件）；**同一帧**里序号高水位前进，并终结所有更低序号的存活范围（“最新者胜”）；持久 ACK 之后才发布到内存（热路径读到的 `scope_epoch` 看不到半个状态）。
- **撤销**：`hy_scope revoke <serial>`，**无需签名**（收紧永远便宜；谁能连上本机套接字谁能撤销，这是操作系统访问控制的事）。执行核心先在内存里标记，使此后的 claim 全部失败；再追加 `ScopeRevoked`，并把高水位提到不小于该序号（对一份从未安装的序号同样有效，它因此永远装不上）；**持久 ACK 之后才向命令行返回成功**。返回内容含“撤销生效时已 claim 的订单”：它们可能已在途，设计不承诺撤回（R-22）。命令行没有收到成功，就是撤销状态未知，Owner 必须当作“可能仍然有效”，需要立刻停手时用熔断。

## 5. 额度（budget）

- **语义**：每份范围的累计“可能已跨越的名义额”，窗口就是它的有效期；不做滚动窗口（想要每天一份额度，就每天签一份，有效期上限使这成为常态）。单位是计价资产最小单位的整数，全程 checked 算术（Engineering Mandate §5）：计数器不得回绕，下溢与溢出是缺陷。
- **收费的时点**：`Prepared` 帧携带 `scope_serial`（0 表示该单由逐单 CONFIRM 授权，非 0 表示范围）；金额由同一帧里的价格与数量重算，不另存。收费因此**与 Prepared 同一次追加**，热路径没有新增的持久追加。帧里放在哪个字段（`detail_code` 或载荷升版）由实现切片定，须过 `tools/spec_enum_diff.py` 与恢复扫描。
- **准入（取代 Gate 11）**：范围存活、静态限额（品种、方向、类型、单笔、敞口、价格偏离、策略版本）通过、预算足够，三者通过才在内存里预占额度；之后任一道门拒绝，预占归还。预占只在内存；它在 `Prepared` 持久 ACK 时成为持久收费。预占是对缓存行对齐的原子计数器的一次检查加增量，热路径零堆分配、无系统调用、无磁盘等待（Engineering Mandate §1、§2）；`scope_epoch` 与计数器放在不同的缓存行，避免伪共享。
- **计数器恢复**：重启后由持久的收费帧**重算**，不依赖任何内存值或快照；恢复为 `Ambiguous` 的订单继续占用额度。
- **归还**：只凭正向证明：① 持久 `NotSent`（最终门拒绝，`docs/NOTSENT_CLOSURE_DESIGN.md`）；② D5 操作员工具对“从未发出”的证明；③（待实现切片核实）交易所终局且成交量为 0 的订单，收费改记为实际成交名义额。**禁止“泄漏防护”超时释放**：一个恢复为 `Ambiguous` 的订单可能已经在交易所成交，给它退额度等于凭空多出一笔授权。
- **耗尽**：新的准入被拒；只减风险的退出不受影响（原则 6）。
- **跨范围**：每份范围的额度独立。新范围不继承旧范围已花的额度，也不被它占用；这是有意的——重新签署是 Owner 的一次明确动作。总风险仍受机器硬上限（敞口）约束，旧范围下已经可能跨越的订单继续占着旧范围的额度，直到被证明或终局。

## 6. 最终门里的消费

范围的消费点就是 `5.9.2` 的最后一门，在 `Prepared` 持久 ACK 之后、取得 claim 之前，**与 claim 同一个线性化点**（`docs/NOTSENT_CLOSURE_DESIGN.md` §4.2）：

1. 七项检查之外增加**第八项**：订单所属的范围仍然存活——序号仍是当前存活序号、没有被撤销、没有被熔断终结、按 §7 的上界估计尚未过期、时钟令牌有效。
2. “范围仍存活”与 claim 是同一次比较并交换：claim 同时校验 `scope_epoch` 与准入时一致（撤销、替换、熔断终结都使它前进）。先查一遍再 claim 不构成证明（`5.9.2` 的“七次独立 load 后普通 call”）。模型的 `AtomicScopeClaim` 开关证明了这一点。
3. 任一检查失败：与其他最终门拒绝同一条路径——`NotSent` 闭合（类 B），收费归还；拒绝原因里新增“范围不再存活”（撤销、被替换、过期、熔断终结各一个值，取值随实现 PR 分配）。
4. 撤销与 claim 的两种次序（R-22）：撤销先线性化，则该单不能 claim；claim 先发生，则该单已可能在途，撤销者必须按“可能已发出”处理。模型的 `SentThenRevokedNeverHappens` 探针显示这个场景可达，设计只承诺“先到的撤销赢”。
5. 决定字是进程内局部变量还是在途槽位里的原子字，取决于发送与撤销是否在同一线程（NotSent 设计 §4.2 第 3 条）；撤销来自本机套接字的线程，所以按“撤销者在另一线程”设计：`scope_epoch` 是原子字，带 TSan 负控（把配对降成 relaxed 必须被抓到）。这是实现切片 S-D 的并发设计，不在本文冻结。
6. 范围检查是**合取**：它不替代、也不能绕过熔断、敞口、限流等任何机器门（原则 2）。**未接线、没有存活范围、范围过期，在“范围模式”下一律拒绝**（沿用 `SubmitReadyToken` 的“未接线即拒绝”）。

## 7. 时间与有效期

- **到期是绝对时刻。**`not_after_ms` 是 Owner 签署的瞬间，重启之后重新判定，不重新计时。把它换算成“从安装起有效 N 秒”并在重启后重新起算，是一类真实的缺陷：一次接近到期的重启就给了范围一份新的租约（模型 `AbsoluteExpiry`）。
- **用上界估计。**判定“尚未过期”用服务器时间的**上界**：本地 UTC 加偏移，再加不确定度 δ；上界仍不大于 `not_after_ms` 才算存活。δ 取令牌所依据快照的 `error_bound_ms` 加 `kMaxClockDriftMs`；快照 TTL 内的晶振漂移是否还要再加一项，由实现切片用实测算出，不手填（模型 `PessimisticExpiry`）。**不得复用 `try_get_pessimistic_server_now_ms()`**：它的悲观是对“K 线是否已收盘”而言的，给出的是下界（只会落后），用在过期判定上方向恰好反了。需要一个新的、方向相反的函数。
- **时钟令牌无效则失败关闭**（`issue_clock_ready_token()` 没有给出令牌）：时钟从未同步、快照过期、墙钟跳变都落在这里；不回退到本地时钟（模型 `RequireClockToken`）。本地时钟被回拨的结果因此是拒绝，而不是一个“又有效了”的旧范围。
- **有效期上限**：签署工具有默认值，**执行侧另有硬上限**（只能收紧，配置在执行侧，D7）；超过上限的范围装不上。上限使“一份被泄露或回滚出来的旧范围”能造成的损害有一个时间界。

## 8. 熔断、撤销与替换

- **新范围终结旧范围。**`LatestWins`：安装序号 n 的同一个原子写里，所有更低序号的存活范围一并终结。否则 Owner 签一份更窄的范围，旧的宽范围仍然有效，收紧就失效了。
- **持久熔断终结存活的范围。**SAFE-04 的持久锁存帧在重放时的规则：该帧之前安装的所有存活范围都变为已终结（原因：熔断）；解除锁存（只有操作员动作）**不使它们复活**，恢复自动下单需要 Owner 重新签一份新序号的范围。这使“事故之后恢复”成为一次有意识的重新授权，也给了他收紧的机会。它对 SAFE-04 提出一个要求：锁存帧与范围终结必须在**同一次原子追加**里（或由重放规则隐含），否则锁存已持久而终结还没写入时崩溃，重启后范围又有效了（模型 `KillInvalidatesScope`）。从哪一级熔断开始终结（推荐 `Triggered` 起；`Armed` 只拦截新开仓）随 SAFE-04 定（D4）。
- **撤销不是紧急停止。**紧急停止是熔断（只减风险）；撤销是收回授权，二者独立，熔断永远优先。

## 9. 回滚与存储（含声明的限度）

“回滚不能复活旧范围”分三种情形，防线不同；第四行是声明的限度，不是防线：

| 情形 | 防线 | 结论 |
| :-- | :-- | :-- |
| 重放一份旧的已签署文件（含已撤销、已被替换、从未安装的序号） | 序号高水位（撤销也推高它）；`store_uuid` 绑定；有效期上限 | 模型 `ReplayGuard`、`LatestWins` 证明 |
| 存储被清空或换成一个空的（新盘、删目录、新虚拟机）：高水位回到 0，旧文件的序号“又是新的” | **范围绑定存储身份**：新存储有新的 `store_uuid`，旧范围验不过；Owner 必须为新存储重新签署 | 模型 `BindStore` 证明 |
| 日志尾部被截断或丢帧 | 继承的尖端锚点检测：锚点序号大于日志尖端即“尾部删除”，`Corrupt`，失败关闭（`durable_audit_sink.hpp:finalize_scan_with_anchor_check`）；范围状态与订单收费必须由同一次恢复一并读取，任何一边缺失或新旧不一致（例如收费帧指向一个控制面日志里没有安装过的序号）= 启动失败关闭 | 继承；本设计只增加一致性检查 |
| **把整个存储恢复成一份较旧但自洽的副本（同一个 `store_uuid`）** | **本地无法检测。** | **声明的限度**，不由本设计证明 |

最后一种的缓解，**均为设计目标，尚未实现**：① 有效期上限（损害的时间界）；② **交易所侧见证**：对账扫描发现带本系统 `HY-` 前缀、其时间戳晚于日志最后一帧、或根本不在日志里的订单，视为日志回卷或外部下单，熔断并升级（树里目前没有“交易所有、日志没有”的订单检测，它是这条缓解要新增的，切片 S-I）；③ 运维规则：恢复任何存储备份之后，把全部已安装范围视为不可信，先熔断，再由 Owner 为新序号重新签署。

范围帧与订单帧放在同一个日志流还是两份日志（控制面日志加恢复期一致性检查）是 S-B 的设计点（D9）：同一个流有一个锚点、没有互相错位的可能，但 256 字节帧装不下一份范围，需要改帧格式；两份日志不动订单帧格式，但需要跨日志的一致性检查。**本文冻结的是要求**（上表第三行），不是布局。执行主机被攻陷不在本设计之内（攻击者可以直接使用 API 密钥）；备机接管时范围随存储走，接管后的第一单仍走最终门，且时钟令牌必须新鲜（任务 6.7）。

## 10. 替换逐单 CONFIRM 的条件与阶段

**只替换 Gate 11 的逐单下单确认。**D5 的操作员确认短语、熔断解除、主备接管、设备与密钥变更等人工动作不变（R-20：危险锁存不自动解锁）。范围是**另一个授权来源**，不是对 `OrderConfirmation` 的修改：每个订单的审计记录它由哪个来源授权（`scope_serial` 为 0 即逐单确认），不得两者皆无，**不在两者之间自动回退**。

| 阶段 | 内容 | 进入条件 |
| :-- | :-- | :-- |
| 0 现状 | 逐单 CONFIRM；没有范围代码 | — |
| 1 影子 | 范围检查随构建存在，**只观察**：对每个订单算出“按范围会怎样”，记审计，与实际逐单确认对照；类型与构建开关使影子路径拿不到发送权，也不能拒绝 | 实现切片合入、`SCP-*` 全部通过 |
| 2 Testnet 强制 | Testnet 上范围是唯一授权（软件测试密钥）；Production 仍逐单 | 影子阶段在 Testnet 上零不一致（次数 `UNCALIBRATED`） |
| 3 Production 首份范围 | Owner 签一份刻意很小的范围（品种、额度取值 `UNCALIBRATED`）；前置：存储里有 Owner 的**首单声明** | 下面的验收证据全部满足，且 Owner 在聊天里明确批准 |
| 4 放宽 | Owner 逐次签署更大的新序号范围；放宽永远是一次签名，不是配置改动 | 每次由 Owner 决定 |

**首单声明**（D5）：Production 范围安装的前置条件是存储里有一份 Owner 用同一把 Production 密钥签署的“首笔订单已由我本人完成”的声明（绑定存储、环境、账户，走与范围同一条验签路径，域分隔不同）。它把“首笔实盘订单仍由 Owner 本人执行”从一条口头规则变成机制：没有它，范围装不上。

**“独立验收”**（R-20“新授权合同须单独验收”的含义，本文的定义）：① 模型与它全部必败配置在 CI 绿（本切片）；② 实现切片的 `SCP-*` 全部通过，含 `thread` 与 `address` 层级，撤销与 claim 的 TSan 负控仍然失败；③ 关键行的变异检查全部被杀死；④ 阶段 1 的影子记录与阶段 2 的 Testnet 运行记录；⑤ 任务 1A.6、SAFE-04、1A.7、SAFE-07 已完成并验收；⑥ 一次独立于实现者的评审没有 P0 与 P1（评审者由 Owner 指定）；⑦ Owner 明确批准进入阶段 3。

## 12. 形式化模型 `formal/scope_approval.tla`

沿用 `notsent_closure.tla` 的惯例：布尔开关常量，`TRUE` 是设计；**关掉任何一个都必须出反例**，这是模型不至于空转的保证；外加可达性探针，防止不变量因为场景不可达而空成立。耐久写在模型里是一步原子的（要么落盘，要么崩溃在它之前）；迟到落盘只会使额度更紧，不会更松，其细节由 `notsent_closure.tla` 证明，这里不重复。

**检查的性质**：`BudgetNeverExceeded`（可能已跨越的订单数不超过预算，跨崩溃、恢复、重放与存储清空）；`NoClaimAfterRevokeAck`；`NoClaimUnderSuperseded`；`NoClaimUnderKilledScope`；`NoClaimAfterExpiry`（按**真实**时间，而不是执行侧的信念）；`NoClaimWhileKilled`；`ClosedImpliesNeverCrossed`；`LiveGrantsAreSigned`；以及三个结构性不变量 `CrossedImpliesDurableCharge`、`MemoryCountsMatchOrders`、`HWMCoversStatuses`。

**十二个开关**（每个对应一份必败配置，报告的不变量见 `formal/README.md` 的表）：

| 开关 | `FALSE` 意味着 | 设计里的位置 |
| :-- | :-- | :-- |
| `AtomicScopeClaim` | “范围是否仍存活”与 claim 是两步，claim 信任旧答案 | §6 第 2 条 |
| `ChargeBeforeClaim` | 收费在发送之后才追加 | §5 |
| `RebuildFromLog` | 重启后计数器从零开始，不从持久帧重算 | §5 |
| `ChargeHeldUntilResolved` | “泄漏防护”给 `Ambiguous` 订单退额度 | §5 |
| `ReplayGuard` | 任何有效签名的范围都能安装 | §4、§9 |
| `BindStore` | 范围不绑定存储身份 | §3、§9 |
| `LatestWins` | 新范围不终结旧范围 | §8 |
| `RevokeAckAfterDurable` | 内存里记下就告诉 Owner“已撤销” | §4 |
| `KillInvalidatesScope` | 熔断只拦截，不终结范围 | §8 |
| `AbsoluteExpiry` | 到期换算成时长并在重启后重新起算 | §7 |
| `RequireClockToken` | 时钟令牌无效时仍用本地时钟 | §7 |
| `PessimisticExpiry` | 直接比较原始读数，不加不确定度 | §7 |

**环境假设**（不在模型里）：A1 签名方案可靠；A2 尖端锚点检测日志截断，**不**检测整份旧副本的恢复（§9）；A3 持久熔断存在且不被重启清除（SAFE-04，今天没有）；A4 同一时刻只有一个执行进程（任务 6.7）；A5 D5 工具只对确实从未发出的订单出具证明。

**不在模型里**：签名本身；范围的静态限额（品种、单笔、价格偏离、敞口：订单的纯函数，没有状态，单元测试即可）；帧布局；多进程；决定字与 NotSent 协议本身（`notsent_closure.tla`）；预算的单位（模型数订单，实现数名义额，协议性质不依赖单位）。**模型不证明实现，也不声称进展**：一个什么都拒绝的系统满足这里的全部不变量，所以才有探针。

结果（TLC 2.19，Java 25，16 个 worker）见 `formal/README.md`。
